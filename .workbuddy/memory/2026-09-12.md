### 引用胶囊显示 `?` —— **不是解析失败**（用户问"是解析失败了吗？"）

**结论**：markdown 侧全对。`[cite:x]` → `preprocessCitations` 归一成 `[citation](x)` → `parseCitationRef` 解析成功 → 胶囊正常渲染，**只是序号解不出来**。

**判定链**（四步）：
1. `MarkdownRenderer` 取 `label/destination` → `resolveCitationCapsule`（或 `label=="citation"` 的内联分支，L1219-1235）
2. `resolver(id)` = `HomeScreen` 里查本消息的 `searchItems`
3. `searchItems` = `extractCitationItems(msg.parts)`，**白名单只认 `search_web` / `builtin_search`**（`CitationSourcesSheet.kt` L143）
4. `info.index == null` 且 `ref.indexText == ref.id` → 回落 `"?"`

**根因 = 来源白名单**：任何别的工具（含 MCP）即便被模型引用，结果也进不了 `searchItems` → 该消息所有引用变 `?`。
**原项目同一白名单**（`chat_message_widget.dart` `_allSearchItems` L3543）→ **上游设计，不是移植偏差**。

**设备取证**（这次靠 DB 取证而不是猜，值得复用）：
- 会话「旅游出行准备」(`404d76b2…`) order 7 的助手消息，**0 个搜索 part**，8 个 `[cite:cmtx…]` 全变 `?`

- 正文里只有 `AIHOT：https://aihot.news/items/cmtxvt03h068vrous6ilk8ds7` 这类 URL → **模型把 URL 末段（cuid）当 id 写进 `[cite:…]`**
- 屏幕截图确认：4 个胶囊渲染出来了、里面是 `?`（证明不是解析失败）

**取证的关键坑**：`message_part_rows` 的关联列是 **`revision_id` → `message_rows.id`**；`part_id` 是 INTEGER AUTOINCREMENT 主键，不是消息 id（我第一版按 `part_id` 分组 → 全表查不到引用，差点得出"没问题"的错误结论）。

### Toast 一多就卡 —— 计时器放错了层（真 bug，已修）

**根因**：原项目在 `AppSnackBarManager.show()` 里就起 `Timer`（`snackbar.dart` L78），**与是否渲染无关**。移植版写成了 `ToastItem` 内的 `LaunchedEffect(entry.id) { delay(durationMs) }` → **只有 `MAX_VISIBLE`(=3) 条被渲染的 toast 会到期**；排队在后面的条目**永远留在队列里**，等它终于升进可见窗口时又重播一遍入场动画 + 重新数 3 秒。

**修法**：`SnackbarManager.show()` 起 `delay(durationMs)` → `expire(entry)`（置 `expiring` 触发淡出）→ `delay(EXIT_MS)` → `removeNow`；**只跑 `delay`**。
- **差点踩的坑**：`Animatable.animateTo` 要求协程上下文里有 `MonotonicFrameClock`，管理器那种 `CoroutineScope(Dispatchers.Main)` **没有**，直接调会抛。所以**动画留在 item（组合内），管理器只管时间**：item 用 `animateFloatAsState` 跟随 `entry.expiring`，入场用「先 compose 成 0、首帧翻 1」。
- 顺带补渲染循环的 `key(entry.id)`：此前按**位置**匹配，一条消失会让槽位错位、Compose 拿别的 entry 复用同一个 composable（状态被重置，整叠乱跳）。
- 回归测试 `app/src/test/.../snackbar/ToastQueueTest.kt` 7 例：Robolectric `shadowOf(Looper.getMainLooper()).idleFor(...)` 驱动 `Dispatchers.Main` 上的 `delay`，**不用真实等待、不需要动画帧**（这套「Robolectric 驱动协程 delay」的写法值得复用）。

## 本批次踩到的两个真 bug（测试抓到的，务必记住）

1. **SigV4 的百分号编码必须大写十六进制**。`awsEncode` 一开始用了小写（`%2f`/`%2a`）——签名照样能算出来，但 S3 会回 `SignatureDoesNotMatch`。
   注意方向相反：**签名串本身是十六进制小写**（Authorization 里那串）。Dart 的 `Uri.encodeComponent` 与 Java 的 `URLEncoder` 都是大写。
   → 用 AWS 官方向量锁死（`GET /test.txt` + `Range: bytes=0-9`，20130524T000000Z → `f0e8b8…6bdb41`），这是唯一能在没有 bucket 的情况下证明 canonical request 逐字节正确的办法。
2. **签名里的 Host 必须省略默认端口**（443/80），因为 HTTP 客户端实际发出的 Host 就是不带端口的；带上就签名不匹配。
   另：`host` 与 `content-length` **不要手动塞进 OkHttp 请求头**（OkHttp 自己按 URL/body 生成，重复写 S3 直接拒），但签名里必须有这两个。
